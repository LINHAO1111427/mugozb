Sub2API 实战使用手册

把一堆 AI 上游账号（OpenAI / Anthropic / 自定义）收口成一个 OpenAI 兼容网关，Claude Code、Codex 全从这儿走。本手册只写真实跑通的路径和能坑死人的点，不抄官网。

00它到底干嘛的

一句话：多账号聚合网关 + OpenAI 兼容协议出口。

你在后台往里塞各种上游账号（OpenAI 的 OAuth 登录态、Anthropic Key、自建兼容端点等），Sub2API 把它们池化，对外只暴露一个标准 /v1 接口。任何支持 OpenAI 协议或 Responses 协议的客户端（Claude Code、Codex、你自己的脚本）都只跟这一个地址说话，账号配额、模型路由、负载都在网关层处理。

为什么不直接用各家官方 SDK因为官方客户端（尤其 Codex / Claude Code）只认一个 base_url。把它们统一指到 Sub2API，你就能在网关里随便换账号、做负载、按模型分流，客户端零改动。

01部署（老老实实用 Docker）

Windows 二进制能跑起来，但有一堆暗病，别碰。

别用 Windows 版 sub2api.exe实测 0.1.177 的 windows binary 有三个坑：① 根本没有 /api/v1 路由（登录直接 404）；② config.yaml 里的 server.port 不生效；③ 时区/TZ 处理有问题。官方 Docker 镜像一个都没有。直接上 Docker。

docker-compose（已验证可用）

两个容器：sub2api（网关本体，镜像 weishaw/sub2api:0.1.177）+ sub2api-postgres（PostgreSQL 17，专给 Sub2API 用，别去动你本机已有的 PG）。Redis 用你机器上已有的 6379 即可。

复制services:
  sub2api:
    image: weishaw/sub2api:0.1.177
    container_name: sub2api
    ports:
      - "127.0.0.1:8088:8080"      # 宿主8088 → 容器8080，避开你别的项目的8080
    environment:
      AUTO_SETUP: "true"           # 首次启动自动建管理员+默认分组
      SERVER_PORT: "8080"
      SERVER_MODE: "release"
      TZ: "Asia/Shanghai"
      DATABASE_HOST: host.docker.internal
      DATABASE_PORT: "55433"
      DATABASE_USER: postgres
      DATABASE_PASSWORD: "你的PG密码"
      DATABASE_DBNAME: sub2api
      DATABASE_SSLMODE: disable
      REDIS_HOST: host.docker.internal
      REDIS_PORT: "6379"
      REDIS_PASSWORD: ""
      ADMIN_EMAIL: admin@sub2api.local
      ADMIN_PASSWORD: "你的管理员密码"
      JWT_SECRET: "随机长字符串"
      TOTP_ENCRYPTION_KEY: "随机长字符串"
    extra_hosts:
      - "host.docker.internal:host-gateway"
    depends_on:
      - sub2api-postgres

  sub2api-postgres:
    image: postgres:17-alpine
    container_name: sub2api-postgres
    ports:
      - "127.0.0.1:55433:5432"
    environment:
      POSTGRES_DB: sub2api
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: "你的PG密码"
    volumes:
      - sub2api-pg-data:/var/lib/postgresql/data

volumes:
  sub2api-pg-data:
两个易错点① 网关容器里 DATABASE_HOST 写 host.docker.internal，必须配合 extra_hosts: host.docker.internal:host-gateway，否则容器找不到宿主 Redis/PG。② 端口映射写成 127.0.0.1:8088:8080 只绑本机，安全；别写成 8088:8080 把端口暴露到全网。

启动

复制docker compose -f docker-compose.sub2api.yml up -d
docker logs sub2api --tail 30   # 看启动日志，确认没报错

02初始化与首次登录

AUTO_SETUP=true 会在第一次启动时自动创建管理员账号和默认分组，不用手动跑向导。

  • 管理后台地址：http://127.0.0.1:8088
  • 管理员邮箱 / 密码：即 compose 里的 ADMIN_EMAIL / ADMIN_PASSWORD
  • 登录走 Web 控制台（不是 /api/v1/auth/login 那个接口，那是给程序调用的，浏览器直接开上面的地址就行）
怎么确认部署成功打开 http://127.0.0.1:8088 能登进后台、左侧能看到「账号 / 通道 / 分组 / 密钥」菜单，就说明镜像、数据库、Redis 链路全通了。如果浏览器都打不开，先 docker logs sub2api 看是不是 PG/Redis 连不上。

03核心数据模型（先搞懂这个，后面不迷路）

Sub2API 的权限/路由是四层结构，一层没接上就报各种"没账号""路由错"。

① 账号 Account
上游凭证池
OpenAI/Anthropic…
→
② 通道 Channel
按上游类型
+ 定价规则
→
③ 分组 Group
按模型名
做路由分流
→
④ 密钥 API Key
客户端持有的
调用凭证

一次请求的完整链路：客户端带 Key 请求 /v1 → 网关找到这个 Key 属于哪个分组 → 分组按"模型名前缀"决定把请求丢给哪个通道 → 通道从它绑定的账号池里挑一个账号 → 账号拿自己的上游凭证去真正调 OpenAI/Anthropic。

绝大多数 401/无账号/路由错误的根因都出在这四层的连接断点上：账号没加进通道的定价规则、账号的 group_ids 是空的、分组类型选错了。第 06、07 节专门讲这两个最阴的点。

04接入上游账号

账号是"上游凭证池"的单元。不同上游接入方式不一样。

OpenAI（OAuth 登录态）

在后台「账号」里选 OpenAI 类型，走 OAuth 授权登录。注意：进网关的是登录态凭证，不是你自己的 sk-。它用的是你那个 OpenAI 账号的配额。

支持哪些模型取决于上游账号的 model_mapping实测你这个 OpenAI 账号支持 gpt-5.6-sol / gpt-5.6 / gpt-5.5 / gpt-5.4 等新一代模型；老的 gpt-4o 不在映射里，调它会报不支持。客户端要的模型名写 gpt-5.6-sol 这类就对了。

Anthropic / 自定义

同理在「账号」里加，类型选对应上游，填 Key 或接入点。多账号时可以加多个，网关会做负载均衡。

05授权了账号，为什么还是调不到

"授权成功"只是把上游钥匙放进保险柜，后面还有三道审批关，全过请求才真正用上你那个账号的额度。

你在后台点几下 OpenAI 授权登录，账号列表里也出现了那个 ChatGPT 账号，信心满满拿 Key 去调 —— 结果要么 no available accounts，要么 gpt-* 请求全跑去 anthropic 报错。这不是授权没成功，是"授权"只是整条链路的第①步，后面三道关没过，请求压根没落到那个账号上。

先分清：账号"在列表里" ≠ "能被调用"授权只是把上游凭证存进网关。真正干活的是通道，而通道、分组、Key 是一道道审批流程。任意一环断了，你那个账号的额度就用不上。

授权之后还差哪三道关

  • 关① 通道没纳管账号（account_stats_pricing_rules）：账号在列表 ≠ 能被调度。通道才是真正发请求的，得用 account_stats_pricing_rules 把账号挂进通道，并声明它支持哪些模型（pricing 的 models 必须非空）。没这步，网关不知道"这个账号能服务哪些模型"，直接报 no available accounts。（详见第 06 节）
  • 关② 账号没进组（group_ids）：账号初始 group_ids 是 null，等于哪个组都不归。请求通过 Key 找到分组后，分组去自己名下找账号，发现账号不在这个组里 → 一样找不到。把账号的 group_ids 设成 [1]（默认分组 id）。
  • 关③ 分组类型写死 provider（composite 大坑）：默认分组（id=1）platform 常是 anthropic，于是所有请求（含 gpt-*）被硬塞给 anthropic 通道 → 找不到 OpenAI 账号。改成 platform: "composite" 才按模型名前缀分流（gpt-*→OpenAI，claude-*→Anthropic）。（详见第 07 节）

怎么确认每一关都过了

  1. 后台「账号」能看到你授权的账号，status: active；
  2. 「通道」里对应通道的 account_stats_pricing_rules 含此账号 id，且 pricing 非空；
  3. 该账号的 group_ids 含目标分组（如 [1]）；
  4. 该分组 platform = composite；
  5. curl /v1/responses 返回 200 + 模型回复；
  6. 终极验证：docker logs sub2api 里 security_audit.gateway_check_start 的 provider 字段，调 gpt-* 时应该显示 openai（不是 anthropic）——显示 anthropic 就是关③没过。
一句话记住授权 = 把钥匙放进保险柜；通道 / 分组 / Key = 取钥匙的审批流程。三道关全过，请求才真正用上你那个账号的额度。

06通道与定价规则（最容易被卡的一步）

光有账号还不够，账号得"挂"到通道上，而且通道得声明自己支持哪些模型。

  • 「通道」里 新建通道，选上游类型（openai 或 anthropic 等）。
  • 通道必须配置 account_stats_pricing_rules：
    • account_ids：指向你刚加的账号 id（比如 [2]）
    • pricing：列出该通道支持的模型（必须非空，比如写 gpt-5.6-sol），空了通道等于没活干
不配这条会怎样请求打进来时报 no available accounts / 找不到可用账号。这是新手第一道坎——账号加好了、Key 也生成了，但通道没把账号纳管，链路断在②→①。

07分组路由（最容易踩的坑，划重点）

分组决定"某个模型名该走哪个上游通道"。这里有个默认配置的隐形坑。

分组有 platform 类型

  • anthropic：所有请求都丢给 Anthropic 通道
  • openai：所有请求都丢给 OpenAI 通道
  • composite（推荐）：按模型名前缀自动分流——gpt-* 走 OpenAI 通道，claude-* 走 Anthropic 通道
默认分组是大坑自动建出来的默认分组（id=1）platform 往往是 anthropic。结果你拿 gpt-5.6-sol 来调，它硬塞给 Anthropic 通道 → 直接失败。把默认分组的 platform 改成 composite 就通了。

账号必须"属于"分组

账号记录上有个 group_ids 字段，默认可能是空的。空了等于这个账号哪个分组都不归，请求照样找不到账号。把你要用的账号的 group_ids 设成 [1]（默认分组 id）即可。

怎么验证路由对不对看 docker logs sub2api 里 security_audit.gateway_check_start 那条日志的 provider 字段：本该是 openai 却显示 anthropic → 就是分组类型错了（上面的坑）。

08API Key 管理

密钥是客户端真正持有的东西，绑定到某个分组。

  • 后台「密钥」里 新建，选它绑定的分组（一般就是默认分组）。
  • 生成出来的 sk-... 就是客户端 api_key / Authorization: Bearer 里填的值。
  • 一个 Key 对应一个分组；想换路由就换 Key 或换分组配置。

09本地调用与验证

网关地址就一个：http://127.0.0.1:8088/v1。两个协议都支持。

协议 / 路径用途客户端
/v1/chat/completions标准 OpenAI 兼容脚本、兼容 SDK
/v1/responsesResponses 协议Codex、新一代客户端
/v1/models模型列表连通性自检

用 curl 验证（两种鉴权头都认）

复制# Bearer 方式
curl http://127.0.0.1:8088/v1/responses \
  -H "Authorization: Bearer 你的SK" \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-5.6-sol","input":"ping"}'

# x-api-key 方式（等价）
curl http://127.0.0.1:8088/v1/responses \
  -H "x-api-key: 你的SK" \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-5.6-sol","input":"ping"}'
判活标准以上任一返回 200 且带模型回复，说明账号→通道→分组→Key 全链路通了。返回 API_KEY_REQUIRED 是没带 Key；no available accounts 是通道/分组没接好（回看第 06、07 节）。

10Claude Code 接入（CC-Switch）

Claude Code 本身只认一个 API 基地址，用 CC-Switch 把 provider 指过来最省事。

  1. 装 CC-Switch（Windows 装 msi 即可，会注册 ccswitch:// 协议）。
  2. 在 CC-Switch 里加一个 provider：
    • Base URL：http://127.0.0.1:8088/v1
    • API Key：你第 7 节生成的 sk-...
  3. Claude Code 通过 ccswitch:// 选这个 provider，之后请求就走 Sub2API 了。
Claude Code 走的是 chat/completions 路径它对 Bearer 的处理是正常的，没有 Codex 那个 env_key 的幺蛾子，配好 base_url + key 就行。

11Codex 接入（另一个大坑，必看）

Codex 0.147.0 的自定义 provider 有个反直觉的设定：它不读 api_key 内联字段。

为什么你一直 401在 config.toml 的 [model_providers.custom] 里写 api_key = "sk-..."，Codex 会整个忽略这行。请求打到 /v1/responses 时一个鉴权头都没有，网关自然回 API_KEY_REQUIRED。实测过所有姿势：api_key 内联 / -c 覆盖 / requires_openai_auth=true+OPENAI_API_KEY 环境变量 / 内建 openai provider，全都不带头。唯一能带出 Authorization: Bearer 的是 env_key。

正确姿势：用 env_key + 环境变量

config.toml 里不要写明文 key，改成指向一个环境变量名：

复制[model_providers.custom]
base_url = "http://127.0.0.1:8088/v1"
env_key = "SUB2API_API_KEY"     # ← 关键：从环境变量取 key，不是 api_key 字段
requires_openai_auth = false
wire_api = "responses"          # 0.147 只支持 responses，chat 模式已移除

model_provider = "custom"
model = "gpt-5.6-sol"

然后把真正的 key 放进 Codex 会自动加载的 ~/.codex/.env：

复制# C:\Users\Lin\.codex\.env
SUB2API_API_KEY=sk-你的密钥
改完必须重启 Codex 会话config.toml 和 .env 都是启动时读取的，正在跑的交互会话不会热加载。重启后再跑就不 401 了。实测 codex exec "Reply with pong" 能正常出结果、消耗 token。

14完整功能地图（每个模块怎么用）

后台左侧菜单对应下面这些模块，按"数据从哪来、干什么用、怎么配"逐个说清。

① 账号 Accounts —— 上游凭证池

  • 添加方式：OpenAI 走 OAuth 授权登录（拿的是登录态凭证，不是 sk-）；Anthropic / 自定义兼容端点走填 Key 或 base_url。
  • 关键字段：status（要 active 才调度）、schedulable（是否可被分配）、group_ids（归属哪些分组，默认可能空 → 必须设）、model_mapping（该账号实际支持的模型名，决定客户端能用哪些 model）、credentials（OAuth token / Key，改账号时务必全量写回保留它）。
  • 多账号：同类型加多个账号，网关按调度策略在池子里挑，天然做负载均衡 / 故障转移。

② 通道 Channels —— 真正发请求的出口

  • 上游类型：openai / anthropic / 自定义等，决定请求打给哪家。
  • 纳管账号：通过 account_stats_pricing_rules 把账号挂进来（回顾第 05、06 节），pricing 的 models 必须非空。
  • 计费模式：pricing 里 billing_mode 可设 token（按 token 计费，配 input/output price）或 per_request（按次）。价格留空 = 不计费只转发。
  • 通道级 model_mapping / restrict_models：可在通道层再做模型名映射或限制只放行某些模型。

③ 分组 Groups —— 按模型路由

  • platform 类型：composite（按模型名前缀分流，推荐）、openai、anthropic（具体类型会把组内所有请求写死给该 provider——新手坑，回顾第 05、第 07 节）。
  • 分组是 Key 与账号之间的桥梁：Key → 分组 → 通道 → 账号。

④ 密钥 API Keys —— 客户端凭证

  • 生成时绑定到某个分组；一个 Key 对应一条路由策略。
  • 支持轮换（旧 Key 禁用、发新 Key），不改客户端配置的话就保持绑定同一分组。

⑤ 计费与额度 Billing

  • 用户（Key 持有方）有余额概念：POST /api/v1/admin/users/{id}/balance {balance, operation:"set"} 可设定/增减。
  • 实际上游消耗走账号自己的配额（你授权的 OpenAI 账号额度），网关层余额是给你自己做的"内部记账 / 限速"用的，两者独立。

⑥ 审计与日志 Audit

  • 每次网关请求都会留 security_audit.gateway_check_start 审计记录，其中 provider 字段暴露"这次请求实际被判给哪家"——路由对不对一眼看出（回顾第 05 节判活法）。
  • 日志位置：docker logs sub2api。

⑦ 安全 Security

  • JWT_SECRET：登录态签名，固定值避免重启掉登录。
  • TOTP_ENCRYPTION_KEY：管理员 2FA（TOTP）密钥加密，固定值避免重启丢失 2FA 绑定。
  • 密钥 / 管理员密码别明文散落；生产环境把端口只绑 127.0.0.1 或放内网。
一张图记住模块职责账号=上游钥匙；通道=拿钥匙发请求的窗口；分组=按模型名决定开哪个窗口；密钥=客户端手里的门禁卡。四者齐了，系统才完整可用。

15账号监测方案（设定好，能跑起来看）

"能用"和"一直在用、出问题能第一时间知道"是两回事。下面把监测拆成四块，并给一套可直接跑的巡检。

监测维度

监测什么看哪里异常信号
账号是否在线可调度账号 status=active 且 schedulable=true状态变 inactive / unschedulable → 上游掉线或 OAuth 失效
通道是否覆盖在用模型通道 account_stats_pricing_rules.pricing.models目标模型不在列表 → no available accounts
路由是否正确docker logs 里 gateway_check_start.provider调 gpt-* 却显示 anthropic → 分组没设 composite
近期报错docker logs grep 关键字no available accounts / 401 / provider mismatch
额度 / 用量上游账号自身配额；网关用户余额上游配额耗尽；网关余额触底

一套可直接跑的巡检脚本

把下面内容存成 sub2api-check.sh，配进系统定时任务（或 WorkBuddy 的定时自动化）每 10 分钟跑一次，异常就告警。

复制#!/usr/bin/env bash
# Sub2API 账号/路由巡检
BASE=http://127.0.0.1:8088
read -r TOKEN < <(curl -s $BASE/api/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@sub2api.local","password":"你的管理员密码"}' \
  | grep -o '"token":"[^"]*"' | head -1 | cut -d'"' -f4)

echo "== 账号 =="; curl -s $BASE/api/v1/admin/accounts -H "Authorization: Bearer $TOKEN" | python -m json.tool
echo "== 通道 =="; curl -s $BASE/api/v1/admin/channels -H "Authorization: Bearer $TOKEN" | python -m json.tool
echo "== 分组 =="; curl -s $BASE/api/v1/admin/groups   -H "Authorization: Bearer $TOKEN" | python -m json.tool
echo "== 近 30 分钟路由/错误 =="
docker logs sub2api --since 30m 2>&1 | grep -iE "gateway_check_start|no available accounts|provider|401" | tail -20

监测设定清单

  • ☐ 账号 status=active 且 schedulable=true
  • ☐ 通道 pricing.models 含你实际在用的模型（如 gpt-5.6-sol）
  • ☐ 默认分组 platform=composite
  • ☐ 设定时任务每 10 分钟跑上面的巡检，对 no available accounts / provider 错配 / 401 做关键字告警
  • ☐ 上游账号额度快满时（OpenAI 侧）提前换号或加号进池子
想要"对话就能查"上面这些巡检我已经封装成 WorkBuddy 运维技能 sub2api-ops。以后你直接在对话里说"帮我看看账号状态""验一下 gpt-5.6-sol 的路由对不对""最近有没有报错"，我来调后台接口跑给你看，不用你自己登后台。
